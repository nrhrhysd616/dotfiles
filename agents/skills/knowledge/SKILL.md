# Knowledge Skill

Claude Code と Codex で共有するルール・ナレッジ・スキルを追加・更新する。
**層（公開範囲）と機構（置き場）の判定を誤ると、非公開情報が公開リポジトリに入る。**
この2つの判定を最初に済ませること。

## Step 1: 機構を判定する

| 判定 | 置き場 |
| --- | --- |
| 常に守ってほしい短い行動ルール | `~/.agents/rules/` |
| 必要なときだけ引きたい参照情報 | `~/.agents/knowledge/` |
| 複数ステップの手順・ワークフロー | `~/.agents/skills/` |
| そのプロジェクトにしか当てはまらない | **このスキルの対象外**。プロジェクトのCLAUDE.mdかauto memoryへ |

`rules/` は全文が毎セッション読み込まれる。迷ったら `knowledge/` にすること。
数行で言い切れず解説が要るなら、それは `rules/` ではない。

## Step 2: 層を判定する

| 判定 | 層 | 実体 |
| --- | --- | --- |
| 公開して困らない汎用的な内容 | shared | dotfiles（**public リポジトリ**） |
| 業務・個人固有だが複数プロジェクトで使う | private | `agent-knowledge-private`（private） |
| この端末でしか意味がない | local | `~/.agents/knowledge-local/`（同期されない） |

**shared に書く前に、次が含まれていないか必ず確認する:**

- 組織名・会社名・顧客名・案件名
- ホスト名・IPアドレス・内部URL・エンドポイント
- 認証情報、トークン、鍵、それらの置き場
- 非公開のスケジュールや意思決定の経緯

1つでも該当したら private へ落とす。判断に迷うものも private へ。
後から public にするのは簡単だが、public に出したものは取り消せない。

## Step 3: 重複を確認する

新規作成の前に、同じ趣旨のものが既にないか調べる:

1. `~/.agents/rules/` 配下の `.md` を確認する（既にコンテキストに載っている）
2. 各層の `INDEX.md` を確認する
3. 現在のプロジェクトの auto memory（`~/.claude/projects/<slug>/memory/`）を確認する

見つかったら新規作成せず、そのファイルを更新する。
auto memory 側に同趣旨があるなら、そちらは削除して二重管理を避ける。

## Step 4: 書き込む

パスは必ず `~/.agents/` 経由の絶対パスを使う。symlink がリポジトリへ解決するため、
どの端末からでも同じパスで書ける。リポジトリの実パスを直接書かないこと。

**rules の場合** — `~/.agents/rules/<topic>.md`

既存のトピックファイルに追記するのが基本。新規作成は、既存のどれにも属さないときだけ。
ファイル冒頭にHTMLコメントで「何に関するルールか」を書く
（コンテキスト注入前に除去されるためトークンを消費しない）。
簡潔・命令形で書き、解説は書かない。

**knowledge の場合** — `~/.agents/knowledge/<layer>/<name>.md`

frontmatter（`name`・`description`）を付け、本文の末尾に `**Why:**` と
`**How to apply:**` を書く。auto memory と同じ流儀に揃えている。

**skills の場合** — `~/.agents/skills/<name>/SKILL.md`

frontmatter の `description` に「いつ起動すべきか / すべきでないか」を具体的に書く。
Codex は description の一致でスキルを暗黙起動するため、ここが曖昧だと動かない。

## Step 5: 索引へ1行追記する（knowledge のみ）

該当する層の `INDEX.md` に1行足す:

```markdown
- [トピック名](ファイル名.md) — いつ読むか
```

**「いつ読むか」を必ず書くこと。** 書名だけでは呼び出されない。
索引は毎セッション読み込まれるので、本文を書き換えても索引が変わらないよう、
行はトリガー中心に書く（索引が変わると次セッションのプロンプトキャッシュがミスする）。

## Step 6: コミットする

層ごとに別のリポジトリなので、書いた層に応じて操作する:

| 層 | リポジトリ |
| --- | --- |
| shared | dotfiles |
| private | `agent-knowledge-private` |
| local | なし（コミット不要） |

**push しないと他の端末に反映されない。** ユーザーに確認してから commit & push する。
`git-ship` スキルを使ってもよい。

## Step 7: 報告する

何をどの層のどの機構へ書いたか、パスとともに1〜2行で報告する。
未 push のものがあればそれも伝える。

## 注意事項

- 削除・書き換えは、対象の現在の内容を読んでから行う
- 「このセッションでしか意味がないこと」は記録しない。
  恒久的に効かせたいものだけが対象
- `rules/` が増えすぎるとコンテキストを圧迫する。
  実質的に参照情報になっているルールを見つけたら `knowledge/` への移動を提案する
